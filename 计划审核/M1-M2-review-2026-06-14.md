## 问题清单与整改方案

### P0：M2 `searchSource(keyword)` 没有真正搜索源码

位置：

- `packages/storage/src/schema.ts`
- `packages/storage/src/symbol-repo.ts`
- `packages/cli/src/commands/query-cmd.ts`
- `开发计划/plan.md`
- `开发计划/M2-implementation-plan.md`
- `README.md`

现状：

- `schema.ts` 只有 `symbols_fts(name, doc_comment)`。
- `SymbolRepo.searchFts()` 查询的是 `symbols_fts`。
- `cesium search <keyword>` 只输出 kind、name、parentClass、filePath、startLine。
- README 写的是 “Full-text search across indexed source code”，计划中也叫 `searchSource(keyword)`。

影响：

- M2 的 “Source Retrieval / searchSource” 语义没有完成。
- 搜源码正文中的关键词无法命中，除非关键词刚好在 symbol name 或 doc comment 中出现。

建议整改：

方案 A，推荐，保持 M2 名称不变：

- 新增源码索引表或 FTS 表，例如 `source_fts(symbol_id, name, file_path, start_line, end_line, code)`。
- 在 `index:symbols` 阶段对每个 symbol 读取 `filePath` 对应源码片段并写入 `source_fts`。
- 新增 `SymbolRepo.searchSource(keyword, limit)`，查询源码正文。
- `cesium search <keyword>` 改为调用 `searchSource`，输出 symbol、file path、line range、命中片段。
- 增加测试：搜索只存在于源码正文、不存在于 doc comment 的关键词，应返回结果。

方案 B，收窄需求：

- 将 M2 里的 `searchSource(keyword)` 改名为 `searchSymbol(keyword)`。
- README 改成 “Full-text search across symbol names and doc comments”。
- 明确源码检索只由 `source <symbolId>` 提供，不提供源码全文搜索。

如果按原计划 “Source Retrieval” 理解，建议采用方案 A。

### P1：M1 全量索引性能和进度反馈不足

位置：

- `packages/indexer/src/cesium-source.ts`
- `packages/cli/src/commands/index-cmd.ts`

现状：

- 全量索引 1004 个文件耗时约 419719ms。
- 默认不加 `--verbose` 时，命令长时间只显示 `Indexing symbols...`。
- 180 秒超时验证时数据库只有 4KB，说明很长时间内没有可见写入或阶段性结果。

影响：

- 容易被误判为卡死。
- CI 或自动化执行若默认超时较短，会失败。
- 用户体验不稳定。

建议整改：

- 默认每 N 个文件输出进度，或显示发现文件数后持续输出百分比。
- 将 parse 和 insert 分批处理，不要等全部解析完再一次性写库。
- 优化 parser 的 ts-morph 使用方式，评估是否每文件独立 Project 或复用策略导致性能瓶颈。
- 增加索引耗时基准测试或至少在 README 中记录首次索引预期耗时。
