## M4 问题与修改建议

### P1 `trace` 的符号解析存在误命中风险

位置：`packages/cli/src/commands/trace-cmd.ts`

现状：
- `resolveSymbolId()` 在找不到精确匹配时，会 fallback 到 `searchFts(input, 5)`
- 对 `Camera.update` 这种输入，如果点号解析失败，可能退化到别的 `update` 相关符号
- 这会让用户以为在追踪 `Camera.update`，实际却追踪了其他符号

建议：
- 对带点号输入优先只做精确解析
- 如果输入是 `Class.method`，找不到精确结果就直接报“not found”，不要自动 FTS fallback
- 若要保留 fallback，也应只在用户显式允许模糊模式时启用
- 给 `trace` 增加一个“精确解析失败即退出”的测试

### P1 `trace Camera.update --direction up` 在验收库上无结果

位置：`packages/cli/src/commands/trace-cmd.ts`、`packages/indexer/src/callgraph-extractor.ts`、`packages/indexer/src/cesium-source.ts`

现状：
- 用临时完整索引库执行 `trace Camera.update --depth 2/3` 时，输出只有 `Camera.update` 和 `DeveloperError [new]`
- `--direction up` 直接无结果
- 这说明当前实现虽然能构建 call graph，但对验收目标的覆盖不足，或者命中路径不符合预期

建议：
- 先确认 `Camera.update` 的实际目标是否应该在 call graph 中出现
- 若应该出现，补充 extractor 对 `this.method()` / instance method / static method 的解析测试和修复
- 若不应该出现，则 README / plan 里的验收样例应替换成稳定可命中的符号

### P2 运行库与新建索引库不一致，容易误判完成度

位置：`database/cesium.db`、`trace` CLI、`index:symbols`

现状：
- 现有工作库里的 `trace Camera.update` 没有结果
- 这是旧库未重建造成的，但用户从 CLI 角度看到的就是“不可用”

建议：
- 在 README 或计划里明确：M4 验收必须基于重新执行 `index:symbols` 的数据库
- 或者在 `trace` 命令里给出“数据库未包含 call_edges / 需要重新索引”的提示

### P2 `buildSymbolMap()` 同名符号策略偏保守

位置：`packages/indexer/src/callgraph-extractor.ts`

现状：
- 顶层同名符号只保留第一个
- 这在 Cesium 这种存在大量同名 `update`、`render`、`Scene` 的项目里，可能把边挂错目标

建议：
- 对 top-level 同名 symbol 建立更明确的 key，至少补充 `filePath` 或签名信息
- 或在无法唯一定位时跳过，不要默默选第一个
- 增加同名符号的回归测试

### P2 文档与验收样例需要再收紧

位置：`README.md`、`开发计划/plan.md`

现状：
- README 已经把 `trace` 写成可用能力，这一点和代码一致
- 但验收示例应该与当前稳定输出一致，避免出现“命令存在，但样例不稳定”的情况

建议：
- 将 `trace Camera.update` 这类不稳定样例改成已经在临时库里明确命中的符号
- 或把它标成示例而不是验收命令

### 剩余风险

- `methodOwners` 唯一方法名 fallback 会提升覆盖率，但本质仍是启发式策略。若某个变量调用的 method name 在索引中唯一，但真实对象不是该类，仍可能产生误边。当前策略符合“覆盖率有限提升 + 高精度优先”的折中，但建议继续用真实索引抽样检查误报率。
- `Camera.update upstream` 不应再作为硬性通过标准；应改为“若 TypeChecker 可解析则返回，否则明确作为已知漏报”。
